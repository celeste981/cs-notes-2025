## LLM / Agent：Context Engineering 与 Context Window 管理

- 优先级：P0
- 对应题目：Q1-1、Q1-2、Q1-5

### 先讲人话

不要只把 prompt 当成一句话。真实 Agent 里，模型看到的是系统指令、用户输入、历史记忆、工具结果、检索文档和状态信息的组合。Context 管不好，模型就会遗忘目标、引用错误信息，或者把无关内容当成指令。

### 再讲原理

核心是把 context 当成一层数据架构：哪些信息永远保留、哪些可以摘要、哪些需要检索、哪些必须放在靠前位置。窗口满时常用 Sliding Window、Progressive Summarization、Selective Retrieval、Map-Reduce 压缩等策略。

### 面试怎么说

我会先保证 system prompt、工具 schema、任务目标不被压缩；历史对话按重要性摘要，长文档走检索或分段摘要；同时监控 token per task、压缩触发点和摘要质量，避免为了省 token 丢掉关键约束。

### 易错点

- 只保留最近对话，丢掉最初任务目标
- 把工具返回的大 JSON 原样塞进 context
- 没有 token/cost 指标，优化全靠感觉

## LLM / Agent：Agent Loop、Observation 与无限循环防护

- 优先级：P0
- 对应题目：Q2-0a、Q2-0b、Q2-0c、Q2-5

### 先讲人话

Chain 像固定流程表，Agent 像会边看结果边决定下一步的执行器。Observation 是它“看见真实世界”的步骤，没有 Observation 就是在凭空想象。

### 再讲原理

Agent Loop 通常是 Input -> LLM 决策 -> Tool Call -> Observation -> 更新状态 -> 继续决策。因为控制权部分交给模型，所以必须加 max_steps、重复动作检测、失败熔断、目标达成检查和总耗时预算。

### 面试怎么说

我会把 Agent 每一步都记录为结构化 step，包括 thought/action/tool_result/cost/latency。简单任务不走完整 ReAct，工具之间无依赖时并行调用；一旦出现重复动作、同工具连续失败或超过步骤预算，就降级返回部分结果。

### 易错点

- 把 Agent 当普通一次性 API 请求
- 只设置 max_steps，没有目标达成检查
- Observation 过大导致下一轮模型注意力稀释

## LLM / Agent：Function Calling、Tool Schema 与工具返回值设计

- 优先级：P0
- 对应题目：Q3-0a、Q3-0b、Q3-2、Q3-4

### 先讲人话

LLM 不会真的执行函数，它只是生成“我要调用哪个工具、参数是什么”的结构化请求。真正执行、校验、重试和鉴权都在 Orchestrator 里。

### 再讲原理

高质量 schema 要有清晰 name、description、参数约束和错误语义。工具返回给代码的是结构化对象，返回给 LLM 的应该是去噪后的摘要，避免把几十 KB 原始响应塞回模型。

### 面试怎么说

我会在工具层做参数校验、权限检查和幂等保护；错误用 error_code/message/suggestion 返回给模型，让它能重新规划。工具多到几十个以后，用 Tool Retrieval 动态选择 top-K schema 注入。

### 易错点

- 工具 description 写得像内部函数注释
- 参数只靠模型自觉，不做后端校验
- 错误直接抛异常，LLM 无法基于错误恢复

## LLM / Agent：RAG、Memory 与评估体系

- 优先级：P0
- 对应题目：Q4-0b、Q4-1、Q4-2、Q4-7、Q4-8

### 先讲人话

RAG 不是“向量库一搜就结束”。生产里要处理切块、召回、重排、实时更新、过时记忆、评估和幻觉控制。

### 再讲原理

基础 RAG 是固定 pipeline；Agentic RAG 会让 Agent 根据问题决定查哪里、查几次、是否换查询。Memory 需要区分短期上下文、长期偏好、事实知识和过程经验，并带来源、时间、置信度。

### 面试怎么说

我会先用检索命中率、答案正确率、引用覆盖率和幻觉率做 eval，再调 chunking、hybrid search、rerank、query rewrite。RAG 和 fine-tuning 的选择看知识更新频率和输出格式稳定性：知识常变优先 RAG，格式固定可考虑 fine-tuning。

### 易错点

- 只看向量相似度，不做 rerank
- 旧知识没有 TTL 或失效机制
- 没有 golden set，调参只能凭主观感觉

## LLM / Agent：Observability、Eval、成本与安全防护

- 优先级：P0
- 对应题目：Q6-1、Q6-2、Q6-7、Q7-0a、Q7-2、Q7-4

### 先讲人话

Agent 的失败不是单点异常，而是模型、prompt、工具、检索、权限和上下文一起出问题。没有可观测性和 eval，很难知道到底坏在哪一步。

### 再讲原理

每次任务要追踪 step_count、tool_success_rate、token、cost、latency、retry、fallback、final_quality。安全上默认 LLM 分不清数据和指令，因此 tool result、网页内容、用户输入都要当不可信数据处理。

### 面试怎么说

我会建设离线 golden set + 在线采样评估，Prompt 版本化并灰度发布；预算按任务类型设上限。安全上做 prompt injection 检测、PII 脱敏、工具权限最小化、人工审批和完整审计日志。

### 易错点

- 只监控 HTTP 200，不监控答案质量
- 没有 prompt 版本和回滚
- 把外部网页内容直接当 system 指令拼接

## Golang：逃逸分析、栈/堆分配与 GC 压力

- 优先级：P0
- 对应题目：G3-01、G6-06

### 先讲人话

Go 变量不一定写在哪就分配在哪。编译器会判断变量生命周期，如果函数返回后还可能被用到，就会从栈逃到堆，增加 GC 压力。

### 再讲原理

常见逃逸包括返回局部变量指针、interface{} 装箱、闭包捕获、goroutine 捕获外部变量、运行期大小不确定的对象等。可以用 go build -gcflags=-m 看逃逸原因。

### 面试怎么说

我会先用 benchmark 和 pprof 确认热点，再看逃逸分析。优化时避免热路径不必要的 interface{}、减少临时对象、预分配 slice/map，小结构体不盲目传指针，因为传指针也可能导致逃逸。

### 易错点

- 认为传指针一定更快
- 没有 benchmem 数据就谈优化
- 只看 CPU，不看 allocs/op 和 GC pause

## Golang：三色标记、混合写屏障与 GOGC/GOMEMLIMIT

- 优先级：P0
- 对应题目：G3-02、G3-03、G3-06

### 先讲人话

Go GC 的目标是在程序运行时并发找出还活着的对象，尽量缩短 STW。三色标记是“白色待确认、灰色待扫描、黑色已扫描”的标记过程。

### 再讲原理

并发标记时用户 goroutine 还在改指针，所以需要写屏障防止漏标。Go 1.8 后的混合写屏障降低了重新扫描栈带来的 STW。GOGC 控制堆增长触发比例，GOMEMLIMIT 给容器内存设置软上限。

### 面试怎么说

默认 GOGC=100 通常够用。容器里我会设置 GOMEMLIMIT 到内存上限的 80% 到 90%，再结合 pprof、runtime metrics 看 GC CPU、堆大小和延迟，不会一上来就手调参数。

### 易错点

- 把 STW 说成完全没有
- 只会背三色，不知道写屏障解决什么问题
- 在容器中不设置内存软上限导致 OOM 风险

## Golang：interface 底层、方法集与反射代价

- 优先级：P1
- 对应题目：G4-01、G4-02、G4-05

### 先讲人话

interface 不是“随便装任何东西”这么简单。空接口和非空接口底层结构不同，方法集规则还会影响一个类型到底有没有实现接口。

### 再讲原理

eface 包含类型指针和数据指针；iface 包含 itab 和数据指针。值接收者方法同时属于 T 和 *T，指针接收者方法只属于 *T。反射能动态操作类型，但会损失编译期检查和性能。

### 面试怎么说

我会优先用明确类型和泛型解决问题，只有序列化、ORM、框架基础设施这类需要处理任意类型的地方才用反射。接口赋值可能引发逃逸，热路径上要关注装箱成本。

### 易错点

- 指针接收者和值接收者方法集说反
- 把类型断言和反射混为一谈
- 在业务热路径滥用 reflect

## MySQL：redo log、undo log、binlog 与两阶段提交

- 优先级：P0
- 对应题目：M4-01、M4-03、M4-05

### 先讲人话

redo log 负责崩溃恢复，undo log 负责回滚和 MVCC，binlog 负责复制和归档。三者不是一个东西，面试最怕混着说。

### 再讲原理

InnoDB 先写 redo 保证事务持久性；Server 层写 binlog 支持主从复制。为了让 redo 和 binlog 对同一个事务保持一致，需要两阶段提交：redo prepare -> 写 binlog -> redo commit。

### 面试怎么说

崩溃恢复时，MySQL 会看 redo 的事务状态和 binlog 是否完整：redo prepare 且 binlog 完整则提交，否则回滚。这样能避免主库恢复结果和从库通过 binlog 重放结果不一致。

### 易错点

- 说 binlog 也用于 InnoDB 崩溃恢复
- 不知道 redo prepare/commit 的判断逻辑
- 忽略 Server 层和 InnoDB 层的边界

## MySQL：WAL、刷盘参数与 Online DDL

- 优先级：P1
- 对应题目：M4-02、M4-04、M4-07

### 先讲人话

WAL 是先顺序写日志，再异步刷脏页。这样把随机写数据页变成顺序写日志，提升事务写入性能。

### 再讲原理

innodb_flush_log_at_trx_commit 控制 redo 刷盘，sync_binlog 控制 binlog 刷盘。参数越严格，崩溃丢数据风险越低，但写入延迟越高。Online DDL 通过元数据锁、增量日志或影子表方案降低大表变更影响。

### 面试怎么说

金融核心链路倾向双 1 配置；普通业务可结合 RPO、延迟和吞吐做取舍。大表 DDL 我会先确认版本能力、锁类型、回滚成本和主从延迟，再考虑 gh-ost/pt-osc。

### 易错点

- 只会说双 1 最安全，不会讲成本
- 大表直接 ALTER 不评估锁和复制延迟
- 把 Online DDL 理解成完全无锁

## Redis：RDB/AOF、fork + COW 与持久化选型

- 优先级：P0
- 对应题目：R3-01、R3-02、R3-03、R3-05、R3-06

### 先讲人话

Redis 持久化不是简单“开不开 AOF”。RDB 是快照，AOF 是追加命令，fork 子进程时会用 COW，但大内存实例仍可能出现延迟。

### 再讲原理

BGSAVE/BGREWRITEAOF fork 后父进程继续处理请求；父进程写到旧内存页时触发 COW 复制，写入越多内存放大越明显。AOF everysec 通常最多丢约 1 秒数据，always 更安全但更慢。

### 面试怎么说

生产选型要看 Redis 是缓存还是准存储。纯缓存可以弱化持久化并依赖 DB 回源；关键数据至少开启 AOF everysec 或混合持久化，并避开高峰重写、监控 fork 耗时和 COW 内存。

### 易错点

- 以为 fork 后完全没有内存成本
- 只说 AOF 更安全，不谈写放大和恢复速度
- 在大实例高峰期触发重写

## Redis：缓存一致性、热点 Key 与多级缓存

- 优先级：P0
- 对应题目：R5-01、R5-02、R5-03、R5-04、R5-06

### 先讲人话

缓存问题本质是“缓存比数据库快，但缓存不是权威数据源”。穿透、击穿、雪崩、双写不一致都是围绕这个矛盾。

### 再讲原理

常见策略包括空值缓存、布隆过滤器、互斥锁、随机过期、逻辑过期、延迟双删、订阅 binlog 删除缓存、本地缓存加 Redis 的多级缓存。没有一种方案能无代价强一致。

### 面试怎么说

我会按业务容忍度选方案：读多写少可以先更新 DB 再删缓存，配合延迟双删；一致性要求更高时用 Canal 订阅 binlog 做最终一致。热点 Key 要提前发现、打散、限流和降级。

### 易错点

- 承诺 Redis 和 DB 强一致
- 热点 Key 只靠扩容 Redis
- 本地缓存没有失效广播或版本控制

## Redis：分布式锁、Lua 原子性与 Redlock 争议

- 优先级：P0
- 对应题目：R6-01、R6-02、R6-03、R6-05

### 先讲人话

分布式锁最重要的是“锁必须有唯一持有者、必须能过期、释放时不能删别人的锁”。SETNX 再 EXPIRE 分两步会有原子性漏洞。

### 再讲原理

正确基础写法是 SET key value NX EX；释放锁用 Lua 校验 value 后删除。Redisson watchdog 通过续期缓解业务执行时间超过 TTL 的问题。Redlock 在时钟、网络分区和强一致语义上有争议。

### 面试怎么说

如果只是防重复提交或弱互斥，Redis 锁足够；如果是金融扣款这类强一致资源协调，我会优先考虑数据库事务、唯一约束或共识系统，不把 Redlock 当万能锁。

### 易错点

- 释放锁不校验 value
- 业务执行超时导致锁过期后并发进入
- 把 Redlock 说成绝对安全

## Redis：线程模型、BigKey、Pipeline/SCAN 与数据建模

- 优先级：P1
- 对应题目：R7-01、R7-02、R7-03、R7-04、R7-07、R8-02、R8-08

### 先讲人话

Redis 快主要是内存操作、事件循环、IO 多路复用和简单数据结构。单线程指的是命令执行主路径，不代表所有后台任务都单线程。

### 再讲原理

Redis 6 多线程主要处理网络 IO，命令执行仍需注意阻塞。BigKey 会阻塞事件循环、放大网络和删除成本。Pipeline 减少 RTT，MGET 是服务端批量命令，SCAN 是渐进式遍历。ZSet 常用于滑动窗口限流、延迟队列和排行榜。

### 面试怎么说

我会禁用生产 KEYS，改用 SCAN 分批；BigKey 用 lazyfree、分批删除或数据拆分治理。秒杀场景会把限流、库存预扣、队列削峰和异步落库组合起来，而不是只靠一个 Redis 命令。

### 易错点

- 说 Redis 6 以后命令并行执行
- 用 KEYS 查生产全量 key
- BigKey 直接 DEL 导致长时间阻塞

### 结合我的经历
