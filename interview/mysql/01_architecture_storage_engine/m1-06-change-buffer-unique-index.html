Change Buffer 是什么？为什么唯一索引不能用？

先讲人话 两条路径 点选理解 面试说法

这题到底在问什么

它不是单纯问 Change Buffer 的定义，而是在问普通二级索引和唯一二级索引的写入路径差异。普通索引可以把索引页修改先记下来，后续再合并；唯一索引必须马上查重，所以必须读页，无法省掉这次随机读。

普通索引 可以先欠账
唯一索引 必须先查账
Change Buffer 缓存二级索引变更
核心收益 少一次随机读页

先建立直觉

插入一条数据时，InnoDB 不只要写主键索引，也可能要维护多个二级索引。如果目标二级索引页不在 Buffer Pool 中，直接读磁盘页会很慢。Change Buffer 就是“先把要改索引页这件事记下来”，等页以后被读进内存，再一起合并。

Buffer Pool：内存页缓存 二级索引：非主键索引 唯一索引：必须查重

两条写入路径

关键分叉点：目标二级索引页不在 Buffer Pool 中时，普通索引可以延迟，唯一索引不能延迟。

普通二级索引

插入或更新记录，需要维护普通二级索引
↓
目标索引页不在 Buffer Pool
↓
不立刻读磁盘页，把变更写入 Change Buffer
↓
以后页被读取或后台空闲时，再 merge 到索引页
VS

唯一二级索引

插入或更新记录，需要维护唯一二级索引
↓
目标索引页不在 Buffer Pool
↓
必须先读磁盘页进内存，检查是否重复
↓
不重复才插入，重复则报唯一键冲突

点选理解

按场景切换，看 InnoDB 为什么有时能省 I/O，有时不能省。

目标页已经在 Buffer Pool 中，无论普通索引还是唯一索引，都可以直接在内存页上处理。Change Buffer 的主要价值不在这个场景。

对比记忆

维度 普通二级索引 唯一二级索引
是否允许重复 允许 不允许
写入前是否必须查重 不需要 必须检查唯一性
页不在 Buffer Pool 时 可以写 Change Buffer 必须读页进内存
性能差异本质 可能省掉一次随机读 为了正确性不能省这次读

1-2 分钟面试回答

Change Buffer 是 InnoDB 针对二级索引写入的一种优化。当要修改的普通二级索引页不在 Buffer Pool 中时，InnoDB 可以不立刻从磁盘读入这个页，而是先把索引变更记录到 Change Buffer。等后续这个页被读入 Buffer Pool，或者后台线程合并时，再把变更应用到真正的索引页上。这样可以减少随机磁盘 I/O，比较适合写多读少、二级索引页不常驻内存的场景。

唯一索引不能使用这个优化，原因是唯一索引写入前必须立刻检查唯一性。为了确认是否存在重复值，InnoDB 必须访问目标索引页；如果页不在 Buffer Pool 中，也必须先从磁盘读进来。既然页已经读进内存，就可以直接更新索引页，Change Buffer 就没有省随机读的价值了。所以这题本质是在考普通索引和唯一索引在写路径上的性能差异。
