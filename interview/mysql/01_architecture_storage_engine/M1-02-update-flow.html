一条 UPDATE 语句的完整执行流程

执行流程 三类日志 两阶段提交 面试说法

先抓住一句话

UPDATE 不是直接改磁盘。它先走 Server 层解析和优化，再让 InnoDB 找到行、加锁、写 undo log、改 Buffer Pool 里的页、写 redo log；Server 层还写 binlog。提交时用两阶段提交保证 redo log 和 binlog 一致。

update user set name = 'Tom' where id = 10;

你最容易混的点

undo

保存旧值，负责回滚和 MVCC。

redo

保存物理修改，负责崩溃恢复。

binlog

保存逻辑变更，负责复制和恢复。

脏页

内存页已改，磁盘页还没改。

2. Server 层和 InnoDB 层怎么分工

Server 层

负责连接、解析、优化、执行调度和 binlog。它知道 SQL 要做什么，但不直接管理 InnoDB 的数据页和事务细节。

连接器 分析器 优化器 执行器 binlog

InnoDB 层

负责 B+ 树定位、行锁、Buffer Pool、undo log、redo log 和刷脏页。真正的数据修改发生在这里。

Buffer Pool 行锁 undo log redo log Page Cleaner

3. 三类日志一句话区分

undo log

改之前先记旧值。

事务失败时能回滚；快照读需要旧版本时，也可以顺着 undo 找。

redo log

改了哪个页、哪个位置。

脏页没刷盘也不怕宕机，重启后可以靠 redo 重放。

binlog

这条 SQL 或这次行变更做了什么。

主从复制、数据恢复、订阅变更依赖它。

日志 所属层 核心用途 面试记忆
undo log InnoDB 回滚、MVCC 后悔药
redo log InnoDB 崩溃恢复 宕机保险
binlog Server 层 主从复制、数据恢复 业务流水

4. 为什么要两阶段提交

核心是让 InnoDB 的 redo log 和 Server 层的 binlog 对同一个事务保持一致。

第一阶段

redo prepare

InnoDB 先把 redo log 写到 prepare 状态。

第二阶段

写 binlog

Server 层写入 binlog，保证复制和恢复能看到这次变更。

第三步

redo commit

InnoDB 把 redo 标记为 commit，事务提交完成。

宕机场景 恢复时怎么判断
redo 只有 prepare，binlog 不存在 说明 binlog 没成功，事务回滚。
redo 只有 prepare，binlog 存在 说明 binlog 已成功，事务提交。
redo 已经 commit 事务提交。

5. 面试 1 分钟说法

一条 UPDATE 先经过 Server 层的连接器、分析器、优化器和执行器。执行器调用 InnoDB 后，InnoDB 根据索引找到目标记录，把数据页读入 Buffer Pool，对记录加排他锁。修改前先写 undo log 保存旧版本，然后修改 Buffer Pool 中的数据页，页变成脏页，同时写 redo log buffer。Server 层还会生成 binlog event，先写入 binlog cache。事务提交时通过两阶段提交保证 redo log 和 binlog 一致：redo prepare、写 binlog、redo commit。脏页不需要提交时立刻刷盘，后台线程会异步刷盘，只要 redo log 可靠落盘，宕机后就能恢复。
