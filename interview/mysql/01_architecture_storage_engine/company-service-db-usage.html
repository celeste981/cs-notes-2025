一句话定位

项目回答不要只背 MySQL 组件，要把“事实源、连接池、事务、binlog 同步、ES/缓存视图”串成真实服务链路。

类比记忆

MySQL 是原始账本，ES 和缓存是复印件或查询视图；排查时不能只看复印件判断账本有没有记录。

记忆口诀

先事实源，再同步链路，最后查询视图。

答题骨架

业务库是否有数据 -> binlog 是否消费 -> 下游是否写入 -> 查询 DSL/缓存是否正确。

点击式流程拆解

第 1 步

服务入口

O-BFF 或业务服务接收请求并访问 MySQL。

为什么要记：说明你知道数据库不是孤立存在。

第 2 步

连接池

控制连接复用、超时、最大连接数。

为什么要记：连接打满和慢 SQL 经常互相影响。

第 3 步

事务边界

关键写操作用事务保证状态一致。

为什么要记：不要把所有操作都放进一个大事务。

第 4 步

binlog 同步

Canal 等组件消费 binlog，同步 ES 或其他视图。

为什么要记：binlog 链路延迟会导致查询视图滞后。

第 5 步

查询视图

ES/缓存服务查询性能，但不是事实源。

为什么要记：数据不一致时先回到 MySQL 核对。

对比记忆

事实源 MySQL业务真实状态，以事务提交为准。排查第一站。
ES/缓存派生查询视图，可能延迟或 mapping 错。适合查，不适合作为唯一事实判断。

先记住这几个抓手

  • 事实源 MySQL：业务真实状态，以事务提交为准。
  • ES/缓存：派生查询视图，可能延迟或 mapping 错。

容易说错

  • 只看 ES 判断业务数据不存在。
  • 忽略连接池耗尽。
  • 把 Canal 延迟误判为 MySQL 写失败。

3 个自测问题

先查业务 MySQL 是否有事实数据。

把 MySQL 变更同步给下游视图。

连接过多会打满 MySQL，过少会让服务等待。

结合项目时，我会先说明 MySQL 是业务事实源，服务通过连接池访问数据库，关键写操作用事务保护一致性。下游 ES 或缓存通常通过 binlog/Canal 同步形成查询视图，所以视图可能延迟或 mapping 错。排查数据问题时先确认 MySQL 是否有数据，再看 binlog 消费、下游写入和查询条件。
