M4-01 深分页与复合索引优化

总览图表流程对比易错自测口述

一句话定位

深分页慢的关键不是返回多少行，而是 OFFSET 要先扫描并丢弃大量前置行。

类比记忆

Offset 分页像从第一页数到第 488 页再取 1000 条；游标分页像拿着上次最后一条的书签继续往后读。

记忆口诀

深分页两件事：改分页模型，用对索引路径。

答题骨架

WHERE id > lastId AND is_deleted = 0 ORDER BY id LIMIT 1000 + INDEX(is_deleted, id)。

点击式流程拆解

第 1 步

观察 EXPLAIN

type=ALL、key=NULL 说明没有合适索引。

为什么要记：先看执行计划，不要直接猜。

第 2 步

识别深分页

OFFSET 487000 要先处理并跳过前置行。

为什么要记：LIMIT 小不代表成本小。

第 3 步

改游标分页

用 lastId 记录上一批最后位置。

为什么要记：适合批处理和滚动加载。

第 4 步

建复合索引

(is_deleted, id) 支持等值过滤 + 范围扫描。

为什么要记：字段顺序要服务查询条件。

第 5 步

控制回表

SELECT * 可能回表，但每批回表行数可控。

为什么要记：优化目标是减少扫描量。

对比记忆

Offset 分页实现简单，页越深越慢。适合浅分页。
游标分页速度稳定，不能随意跳页。适合批量拉取。

先记住这几个抓手

  • Offset 分页：实现简单，页越深越慢。
  • 游标分页：速度稳定，不能随意跳页。

容易说错

  • 只加索引但保留巨大 OFFSET。
  • 联合索引字段顺序随便放。
  • 忽略 SELECT * 回表成本。

3 个自测问题

要先扫描并丢弃前 487000 行。

先等值过滤，再按 id 范围有序扫描。

不适合任意跳页，需要依赖上一页游标。

我会先看 EXPLAIN，type=ALL、key=NULL 说明没有访问路径；OFFSET 很大说明 MySQL 要先扫描并丢弃大量行。优化不是只加索引，而是把 LIMIT/OFFSET 改成基于 lastId 的游标分页，并建立 (is_deleted, id) 复合索引，让等值过滤和 id 范围扫描都能利用索引。
