日志与崩溃恢复可视化

三大日志 两阶段提交 崩溃恢复 刷盘参数 面试口述

三大日志先分工

undo log

记录旧版本，用于事务回滚和 MVCC。它回答的是：如果事务失败，怎么恢复到修改前？快照读要看旧版本怎么办？

redo log

记录数据页物理修改，用于崩溃恢复。它回答的是：已提交事务的脏页还没刷盘，宕机后怎么补回来？

binlog

记录 Server 层逻辑变更，用于主从复制和归档恢复。它回答的是：从库怎么同步？误操作怎么按时间点恢复？

一次 UPDATE 的提交路径

重点记住：数据页不必在提交时刷盘，但 redo 和 binlog 的一致性必须处理好。

1. 写 undo

保存旧值，准备回滚和 MVCC 版本链。

2. 改内存页

修改 Buffer Pool 中的数据页，产生脏页。

3. redo prepare

InnoDB 写 redo，事务进入 prepare 状态。

4. binlog fsync

Server 层写入完整 binlog event。

5. redo commit

InnoDB 将事务标记为最终提交。

刷盘参数怎么选

innodb_flush_log_at_trx_commit

值含义风险
1每次提交 redo write + fsync最安全，性能成本最高
2每次提交 write，不每次 fsyncOS 崩溃可能丢最近数据
0后台约每秒 write + fsyncMySQL 崩溃也可能丢最近数据

sync_binlog

值含义风险
1每次提交 fsync binlog最安全，性能成本最高
0交给 OS 刷盘OS 崩溃可能丢 binlog
N每 N 次提交 fsync可能丢最近一批 binlog

核心交易链路优先双 1。非核心、可重放数据可以评估放宽，但要先明确 RPO。

1 到 2 分钟面试口述

MySQL 写入链路里，undo、redo 和 binlog 分别解决不同问题。undo 记录旧版本，用于回滚和 MVCC；redo 是 InnoDB 的物理日志，用于崩溃恢复；binlog 是 Server 层逻辑日志，用于主从复制和按时间点恢复。InnoDB 采用 WAL，所以提交时不要求数据页立刻刷盘，只要 redo 按策略落盘，脏页可以后台刷。为了保证 redo 和 binlog 对同一个事务一致，MySQL 使用两阶段提交：redo prepare、binlog fsync、redo commit。崩溃恢复时，如果 redo 已 commit 就提交；如果 redo 是 prepare，就看 binlog 是否有完整 XID，有就提交，没有就回滚。生产上还要结合刷盘参数选择安全和性能的取舍，核心业务一般用双 1。
