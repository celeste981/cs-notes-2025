M5-03 两阶段提交

总览图表流程对比易错自测口述

一句话定位

两阶段提交保证 redo 和 binlog 对同一个事务保持一致。

类比记忆

两个人签字：InnoDB 先准备，Server 层流水确认，再最终盖章。

记忆口诀

prepare 遇崩溃，binlog 有就提交，没有就回滚。

答题骨架

redo prepare -> binlog fsync -> redo commit。

看图记 3 句话

  • 两阶段提交解决的是 redo 和 binlog 的一致性。
  • 崩溃在 prepare 后，要看 binlog 是否完整。
  • 回答时把“有 binlog 就提交，没有就回滚”讲清楚。

点击式流程拆解

第 1 步

redo prepare

InnoDB 写 redo 并进入 prepare。

为什么要记：还不是最终提交。

第 2 步

binlog fsync

Server 写完整 binlog。

为什么要记：binlog 完整是关键判断。

第 3 步

redo commit

InnoDB 标记最终提交。

为什么要记：正常提交完成。

第 4 步

崩溃判断

prepare 状态要检查 binlog XID。

为什么要记：XID 关联同一事务。

第 5 步

提交或回滚

binlog 完整提交，否则回滚。

为什么要记：保证主库和复制链路一致。

对比记忆

prepare + 无 binlog恢复回滚。从库也不会有这笔变更。
prepare + 完整 binlog恢复提交。binlog 可能已被消费。

先记住这几个抓手

  • prepare + 无 binlog：恢复回滚。
  • prepare + 完整 binlog：恢复提交。

容易说错

  • 把 redo prepare 当成提交。
  • 不提 XID。
  • 说两阶段提交解决主从延迟。

3 个自测问题

从库可能已经消费，主库必须一致。

是 MySQL 内部两个日志系统协调。

group commit 合并 fsync。

面试口述

30 秒短答：事务提交先写 redo prepare，再写并刷 binlog，最后 redo commit。

事务提交先写 redo prepare，再写并刷 binlog，最后 redo commit。恢复时 redo commit 直接提交；redo prepare 要看 binlog 是否有完整 XID，有则提交，没有则回滚，从而保证主库恢复结果和 binlog 复制结果一致。
