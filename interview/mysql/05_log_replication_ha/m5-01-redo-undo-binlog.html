三本账：旧账、保险单、流水档案。

写 undo -> 改 Buffer Pool -> 写 redo -> 写 binlog -> 两阶段提交。

看图记 3 句话

  • undo 关注旧版本，redo 关注 crash recovery，binlog 关注 replication。
  • redo 和 binlog 需要两阶段提交保证一致。
  • 面试常追问 WAL、刷盘参数、崩溃恢复。

点击式流程拆解

第 1 步

写 undo

保存旧值，用于回滚和 MVCC。

为什么要记：没有旧值就无法安全回滚。

第 2 步

改 Buffer Pool

在内存页上修改数据，产生脏页。

为什么要记：提交时不要求数据页立刻刷盘。

第 3 步

写 redo

记录页级物理修改，崩溃后重放。

为什么要记：redo 是 InnoDB 的 crash-safe 核心。

第 4 步

写 binlog

记录逻辑变更，用于复制和归档恢复。

为什么要记：binlog 是 Server 层能力。

第 5 步

两阶段提交

协调 redo 和 binlog 一致。

为什么要记：防止主库恢复和从库回放结果不一致。

对比记忆

redo logInnoDB 物理日志，循环写。崩溃恢复。
binlogServer 逻辑日志，追加写。复制和归档。
undo log旧版本日志。回滚和 MVCC。

先记住这几个抓手

  • redo log：InnoDB 物理日志，循环写。
  • binlog：Server 逻辑日志，追加写。
  • undo log：旧版本日志。

容易说错

  • 说 binlog 用于 InnoDB 崩溃恢复。
  • 说 redo 记录 SQL。
  • 忘记 undo 支持 MVCC。

3 个自测问题

binlog 不记录 InnoDB 数据页物理状态。

redo 循环写且 InnoDB 独有，不能长期归档复制。

undo、Buffer Pool、redo、binlog，两阶段提交。

面试口述

30 秒短答：三大日志分工不同：undo 记录旧版本用于回滚和 MVCC；redo 是 InnoDB 物理日志用于崩溃恢复；binlog 是 Server 层逻辑日志用于复制和归档。
