分库扩容迁移：流程、风险和数据覆盖坑

迁移流程 分片映射 风险点 面试说法

先抓住一句话

分库扩容不是“把数据搬过去”这么简单。真正要保证的是：迁移期间业务还在写，旧库和新库最终必须一致；同时要确认分片键、同步唯一键、目标分片数都设计正确，否则可能出现数据覆盖。

分片键

决定数据路由到哪个库。

同步唯一键

决定迁移工具认为哪两行是同一行。

倍数扩容

旧分片到新分片映射更可控。

这个案例的核心坑

旧库每个分片都有本地自增 id，不同库都可能有 id = 100。如果非倍数扩容后这些数据进入同一个新库，而同步工具又只用 id 判断唯一，就会把不同业务数据误认为同一行，发生覆盖。

1. 标准分库扩容流程

1. 评估

容量、QPS、连接数、单分片大小、热点。

2. 设计

新分片数、分片键、唯一键、回滚方案。

3. 建库

创建目标库表和配置路由。

4. 全量

把历史数据整体同步到新库。

5. 增量

通过 binlog 追平迁移期间新增写入。

6. 校验

行数、checksum、业务主键抽样；不通过不能切流。

2. 为什么倍数扩容更可控

8 -> 24：倍数扩容

切换场景

看旧分片数据会不会混到同一个目标分片组里。

3. 扩容前必须审的风险点

风险 1：自增 id 不是全局唯一

分库后每个库都可能从 1 开始自增，不能默认拿它做跨库唯一判断。

风险 2：分片键和唯一键混淆

分片键负责路由，同步唯一键负责判断同一行，两个概念不能混用。

风险 3：校验没过就切流

校验阶段发现差异要停止切流，清理错误数据，修正方案后重跑。

检查项 为什么重要 结果不安全时怎么办
每张表的分片键 决定数据落库是否均匀、查询是否方便。 重新评估路由规则或拆分迁移范围。
每张表的全局唯一键 决定同步工具能否正确 upsert 和去重。 改同步配置，或调整表结构和迁移方案。
新旧分片数关系 非倍数扩容更容易让不同旧分片混合。 优先倍数扩容，或做更严格的唯一键保障。

4. 面试 1 分钟说法

我参与过一次分库扩容迁移问题处理。标准流程是先评估容量和流量，再设计新分片数和分片键，创建目标库后做全量同步，迁移期间通过 binlog 做增量同步，追平后做数据校验，最后才灰度切流。我们遇到的坑是同步工具默认用 MySQL 自增主键 id 判断唯一，但这个 id 只是单库内唯一，不是全局唯一。旧库 8 个分片里不同库都可能有相同 id，非倍数扩容后这些数据可能进入同一个目标库，工具只看 id 就会发生覆盖。这个问题在校验阶段发现后，我们没有切流，而是清理错误新库数据，调整分片方案并补齐分片，重新同步和校验。复盘经验是：扩容前必须审每张表的分片键和全局唯一键，不能默认本地自增 id 可以跨库唯一。
