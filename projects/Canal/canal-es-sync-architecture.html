Canal / ES 同步架构图解

一句话：Canal 把 owner 服务 MySQL 的 binlog 同步成 Elasticsearch 查询视图，支撑 Insurance Admin 的宽表、复杂查询、报表和运营分析。

Markdown 版 项目索引 Insurance 总览

同步链路

记忆主线 Canal/ES 不是业务事实源，而是把 owner MySQL 的 binlog 同步成近实时查询视图。面试按“源库、binlog、server、MQ、adapter、ES、Admin 使用方”这条链路讲。
Owner MySQLProduct / Order / Policy / Marketing 等服务写入事实数据。
BinlogMySQL 记录 insert/update/delete 事件。
Canal Instance模拟 slave 订阅 binlog，解析变更。
Kafka承接 server 到 adapter 的消息，观察 lag。
Adapter加载 datasource 和 sync script，消费并回查。
Elasticsearch写入 index，提供近实时查询视图。
Admin / O-BFF复杂查询、报表、导出、人群筛选。

1 分钟讲法：Canal 是 Insurance 的 MySQL 到 ES 同步基础设施。业务服务写 MySQL 后，Canal 订阅 binlog，把变更消息发到 Kafka，adapter 消费后按 sync script 回查 MySQL 并写入 ES。ES 支撑 Admin 的复杂查询和导出，但它是最终一致查询视图，不是事实源；数据不一致时要沿 MySQL、binlog、Canal、Kafka、adapter、ES mapping、DSL 逐层排查。

配置模型

Instance

Canal Instance

订阅某个 RDS/DB 的 binlog，RDS 扩容时常新增。

Topic

Kafka Topic

如 live-id.tp.spin_es，承接同步消息。

Datasource

srcDataSources

Adapter 回查 MySQL 使用的 JDBC 数据源。

Script

ES sync script

定义 index、SQL、_id、etlCondition、commitBatch。

Mapping

ES Mapping

字段类型决定查询能力，类型错可能要重建索引。

ETL

存量同步

历史数据刷 ES，重点看分批字段和业务主键。

DLQ

异常消息

避免异常消息长期阻塞 partition。

Rollback

回滚物料

旧 script、旧 datasource、旧 instance 状态要提前归档。

操作场景

先确认 ES mapping，再准备 sync script 和 datasource；发布后用测试数据验证 MySQL -> Canal -> Kafka -> Adapter -> ES 全链路。
新增 instance 初始关闭，新 script 预置 is_deleted=1，AT 先验证；切换时停旧 instance、启新 script、发布 datasource、开新 instance、观察 lag/DLQ/ES。
ETL 是存量同步，重点看 etlCondition。聚合型宽表不能随便按表主键 id 分批，否则可能跨批次覆盖 ES 文档。
ES 查不到数据时按层排：owner MySQL -> binlog/slave -> Canal Instance -> Kafka lag -> Adapter/DLQ -> ES mapping -> 查询 DSL。

阻塞优化 / DLQ

Confluence 优化重点 同步阻塞优化的核心目标是：单条脏数据、脚本异常或 ES bulk 局部失败不能长期阻塞整个 partition；正常数据不能丢；异常数据要能进入 DLQ 并支持修复后重试或时间窗口补数。
异常识别区分可重试异常、ES 集群异常、脚本/数据异常。
ETL 阶段回查/转换阶段失败按单条定位，避免整批卡死。
ES Bulk 阶段解析 BulkResponse，把失败 document 提出来。
DLQ Topic异常消息进入 tp.spin_es.dlq 类死信 topic。
人工重试修脚本/修数据后按 DLQ 或时间窗口补刷。
监控面板produce、retry success、final failure 指标可见。
正常 ACK好数据继续消费，异常数据不拖垮全链路。
优化点面试怎么说
异常分层ES 集群不可用时不能轻易 ACK 丢消息；数据/脚本异常可进 DLQ，避免阻塞其他数据。
BulkResponse 解析Bulk 写 ES 可能部分成功部分失败，要把失败 item 拆出来处理。
DLQ 可观测监控指标包括 DLQ 产生、重试成功、最终失败，并带 destination、config_file、es_index、exception_type。
补数能力异常修复后可以按 DLQ 重试，也可以用 ETL 按时间窗口补刷。
阻塞优化前
坏数据卡批次

单条脚本/mapping/数据异常可能拖住同一批或同一 partition。

ACK 后难恢复

如果异常处理不清晰，可能出现消息确认后难以补偿。

阻塞优化后
好数据继续走

ETL 和 ES Bulk 分阶段拆出失败 item，正常数据不被拖住。

坏数据进 DLQ

异常消息可观测、可重试，必要时按时间窗口补刷。

ES 设计和 ETL 重点

Mapping

字段最小化

避免动态 mapping 膨胀，keyword 只给确实要聚合/精确查询的字段。

Shard

容量边界

按业务数据量规划 shard，关注单 shard 文档数和容量，不盲目加字段。

ID

文档主键

_id 要稳定。聚合宽表不能随便用明细表主键，否则补刷可能覆盖错。

ETL

深分页补刷

大表 ETL 要按 ID、时间或业务字段切片，避免深分页和跨批覆盖。

Template

模板生成

分表多、区域多时用模板生成 sync script，降低手工改错风险。

Rollback

切换回滚

RDS 扩容切换前保留旧 instance、datasource、script 和回滚步骤。

面试要点

问题回答抓手
Canal 为什么重要？Admin 查询复杂且跨分表，不能直接扫业务 MySQL；Canal 提供 MySQL 到 ES 的近实时查询视图。
是否强一致？不是。ES 是最终一致查询视图，事实源仍是 owner MySQL。
sync script 关注什么？dataSourceKey、destination、groupId、_index、_id、sql、etlCondition、commitBatch。
RDS 扩容怎么做？新 instance、新 datasource、新 script、AT 验证、切换、观察、可回滚。
同步阻塞怎么优化？异常分层处理，ETL/ES Bulk 两阶段拆分，失败 item 进 DLQ，正常数据继续消费，修复后支持重试和时间窗口补数。
