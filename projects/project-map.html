项目地图

面试时可以把这些项目讲成一个 Insurance 业务组内的系统群，而不是几个互不相关的服务。

核心业务链路

这张图用来记面试中的主线：Admin 配置和审批通过 O-BFF 进入，Marketing 负责执行营销计划，Marketing-Data 提供离线名单，Canal 把 MySQL 变化同步到 ES 支撑后台查询。

复习路线

不需要每次从所有文件开始看。按这个顺序复习，能避免内容散掉。

1. 部门地图

先把 Insurance 服务群和业务链路讲顺。

 2. 主项目架构

Marketing 是主项目，先记核心模型和主链路。

 3. 技术优化

用 Redis Roaring Bitmap 准备缓存和性能深挖。

 4. 后台治理

 5. 数据链路

补 Marketing-Data 和 Canal，回答离线供数与 ES 同步。

文件放置规则

新增内容前先判断它属于哪一层，避免同一主题在多个目录重复扩散。

部门级内容

放 `Insurance/`。例如业务地图、跨服务流程、统一面试口径、资料来源索引。

服务级内容

放对应项目目录。主架构用 `<project>-architecture.md/html`，模块深挖用 `<project>-<topic>-deep-dive.md`。

图解内容

HTML 和 Markdown 尽量同名；Markdown 顶部要放 HTML 链接；HTML 自包含，不依赖 CDN。

真实性边界

没确认的个人贡献、线上收益、事故结论写 `待补充`。可以讲“组内负责/我熟悉链路”，不要说成“我独立负责全部”。

新增材料 推荐目录 备注
某个 Admin 页面到下游服务的完整流程 O-BFF/ 如果涉及多个服务，再在 Insurance/business-flow-map.md 加一条总览。
Marketing 某个 Processor / Handler 深挖 Marketing/ 同步更新 Marketing/README.md。
离线名单、batch history、Kafka 推送 Marketing-Data/ 和 Marketing 主链路相关时，在 Marketing 文档里只保留边界说明。
Canal sync script、ETL、DLQ 排障 Canal/ 如果支撑 Admin 查询，可以在 Insurance 总览里补一句关系。
