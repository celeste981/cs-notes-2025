O-BFF 架构图解

一句话：Insurance Admin 的后台聚合和治理层，负责把 Admin 请求接入权限、日志、脱敏、审批、批量任务、数据修复、配置化组件和下游服务编排。

一眼看懂

Admin Portal后台页面、权限入口、批量上传、查询、配置、审批动作。
Interceptor重复请求、公共参数、操作日志、更新历史、脱敏、审批信息、proxy、安全日志。
Service / Manager接 API，做后台场景编排，组合中心模块和下游调用。
治理中心Approval、Batch Operate、Task Center、Data Fix、Operator Executer。
下游 OwnerProduct、Order、Policy、Promotion、Marketing、Account、Risk 等事实源。

配置化组件体系

面试主线 O-BFF 不只是手写后台接口。我们把 Admin 常见能力沉淀成 Assembly Proxy、Assembly Import、Assembly Export、Mask、Approval Mapping、Operate History、TaskConfig 这些配置化组件，标准场景配置接入，复杂高风险场景再写 Manager/Biz。
代Proxy 代转标准查询/更新接口走配置化 RPC proxy。
导Import 导入CSV、字段映射、切批、错误明细。
出Export 导出Page/Scroll、S3、下载记录。
脱Mask 脱敏PII 字段统一在 interceptor 处理。
审Approval 审批高风险操作先审批再执行。
史History 留痕操作日志、更新历史、任务记录。
Admin 新需求先判断是不是标准后台能力：proxy、导入、导出、脱敏、审批。
选择组件Assembly Proxy / Import / Export / Mask / Approval Mapping。
生成配置AssemblyTool 或 Admin skills 生成配置表、config-center、batch_task_config。
运行时执行Interceptor、Task Center、Approval Center 读取配置并执行。
验证观测审批记录、任务记录、操作历史、Prometheus、日志。

配置化 vs 手写代码边界
标准 + 低风险Assembly Proxy：查询、简单更新、字段映射清楚。
标准 + 高风险Proxy/Batch + Approval Mapping：先审批，再执行。
批处理 + 可抽象Assembly Import/Export：文件、S3、任务、结果明细统一。
复杂 + 资损手写 Manager/Biz：状态机、幂等、补偿和异常路径显式编排。

面试可按这个 2x2 图回答“什么时候配置化，什么时候写代码”。

典型流程

Admin 上传文件 -> 创建 batch record -> 发起审批 -> 审批通过 -> Task Center 异步执行 -> 调下游批量 API -> 生成成功/失败结果和错误明细。
创建 data fix 记录 -> 填字段和业务 ID -> 审批 -> reliable-event 异步执行 -> 调 owner 服务修复 -> 更新状态并支持失败重试。
Admin 通用接口 -> rpc_proxy/orchestration interceptor -> 前后置处理 -> 下游 RPC -> response 加工。复杂资损链路不要只靠 proxy。
Admin 列表/报表 -> O-BFF 构造查询 -> ES DAO -> 转换展示字段。排障顺序：MySQL -> Canal -> Kafka/Adapter -> ES mapping -> DSL。

优化项重点

Component

配置化组件

Proxy、Import、Export、Mask、Approval Mapping 统一配置，减少重复开发和治理漏接。

Interceptor

公共治理集中化

权限、日志、脱敏、重复请求、审批信息集中在链路入口，业务代码更聚焦。

Batch

批量执行拆层

Batch Operate 管运营记录和审批，Task Center 管文件、远程调用、S3、监控。

Contract

下游契约检查

导入导出前确认分页、幂等、局部失败、错误码和错误信息结构。

Export

大结果集保护

Page/Scroll/SearchAfter、稳定排序、超时和终止条件必须明确。

Observe

监控 label 规范

保留低基数字段，不把 userId、policyId、手机号或原始错误打进 label。

面试怎么说

问题回答抓手
为什么需要 O-BFF？Admin 跨多个下游服务，而且后台操作需要审批、脱敏、日志、批量任务和数据修复治理。
配置化组件怎么讲？标准接口走 Assembly Proxy，导入导出走 Assembly Import/Export，敏感字段走 Mask，高风险操作走 Approval Mapping；复杂状态机和资损链路再手写 Manager/Biz。
怎么避免大泥球？O-BFF 只做 Admin 编排和治理；Product、Order、Policy 等 owner 服务负责领域事实。
批量怎么可靠？任务化、审批、切批、单条错误定位、结果下载、状态可追踪、下游幂等。
数据修复怎么控风险？不直接改库，走修复记录、审批、可靠事件、owner 服务接口和失败重试。
1 分钟讲法：O-BFF 是 Insurance Admin 的聚合和治理层。它先用 interceptor 做权限、日志、脱敏、重复请求和 proxy，再由 Service/Manager/Integrate 编排下游服务。我们还把标准后台能力做成配置化组件：Proxy、Import、Export、Mask、Approval Mapping。这样普通 Admin 需求能快速接入，同时高风险操作仍然有审批、审计、任务状态、失败明细和下游 owner 边界。
