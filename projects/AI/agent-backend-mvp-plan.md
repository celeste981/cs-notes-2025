# Agent Backend MVP：可信度优先的求职项目

> 推荐作为唯一主项目。目标不是做“功能齐全的 Agent 平台”，而是完成一个能独立解释、可运行、可测试的最小生产工程闭环。  
> 业务场景可选：通用运营知识与诊断助手；Voucher 只作为可替换的示例数据域，不是前置条件。
> 启动时机：优先完成六周后端基础、项目表达和 Resume B 主线；建议在第 7-8 周集中完成此 MVP，而非从第一周并行开发。

## 先讲结论

三个月时间紧时，不要承诺多 Agent、复杂 MCP 生态、真实生产写操作、完整管理后台或大量业务 Tool。面试里最有价值的是：你能清楚说明一个 Agent 后端怎样安全地调用工具、保存状态、处理失败、观测质量，并用代码和演示证明其中一部分。

## MVP 范围

### 必做：只保留 5 个证据点

1. **Tool Calling**：2 个只读、可模拟的 Tool，例如 `search_knowledge` 与 `query_task_status`；参数和返回值都有 schema 校验。
2. **RAG + 引用**：从本地 Markdown / 脱敏知识样例检索，答案列出来源；没有证据时回答“不确定”。
3. **Workflow + State**：一次任务有 `task_id`、step、状态和最大步数；状态能持久化到 SQLite/PostgreSQL 之一。
4. **失败治理**：至少展示 timeout、一次有限重试、结构化错误和幂等的任务创建。
5. **Trace + Eval**：记录模型/工具耗时、步骤和 token（或估算成本）；准备 10-20 条脱敏测试集，输出通过率和失败样例。

### 只选一个加分项

- 异步长任务：用队列或 background worker 执行一个耗时诊断任务，并支持查询状态；或
- 审批模拟：对“生成操作建议”展示审批状态机，但不接真实写操作；或
- MCP：把一个只读 Tool 做成 MCP Server，并说明 MCP 只解决接入协议，不能替代权限和审计。

三者不要同时做。建议优先选 **异步长任务**，因为它和现有后端经验的衔接最强。

### 明确不做

- 多 Agent 协作、复杂规划、自主浏览网页、聊天 UI、美化大屏。
- 真实 Voucher 配置写入、真实生产库连接、真实权限体系或复杂审批流。
- 为了简历而堆 LangGraph、MCP、向量库、模型等名词；没有代码和讲解把握的组件不写进简历。

## 推荐技术栈（可替换）

| 层 | 推荐最小选择 | 原因 |
| --- | --- | --- |
| API | Python + FastAPI | 学习曲线低，方便接 LLM SDK；不需要证明 Python 很深 |
| 编排 | 简单显式状态机；时间充足再用 LangGraph | 先能解释状态转移和失败恢复，再使用框架 |
| State | SQLite 起步 | 单机可运行、可演示；不因基础设施拖慢交付 |
| RAG | 本地 Markdown + 简单检索/轻量向量检索 | 重点是来源、权限过滤思路和评估，而非向量数据库品牌 |
| 观测 | 结构化日志 + trace_id + 本地 trace 页面/JSON | 足以证明可回放、可排障 |
| 测试 | pytest + 固定测试集 | 防止模型/Prompt 改动后悄悄退化 |

如果 FastAPI/Python 基础尚弱，可以先用 Go 写 Tool / 任务服务，Python 只承担 Agent API；但不要为了双语言架构额外增加交付风险。

## 两周完成的最小里程碑

| 时间 | 只做什么 | 可验证产物 |
| --- | --- | --- |
| Day 1-2 | 定义一个任务："根据知识库回答问题并查询任务状态"；建立 10 条知识样例 | README、数据样例、接口契约 |
| Day 3-5 | 接入 LLM、两个只读 Tool、schema 校验和引用返回 | 可录制 2-3 分钟 Demo |
| Day 6-8 | 加 task state、timeout、一次重试、结构化错误 | 失败场景能演示且能解释 |
| Day 9-10 | 加 trace 和 10-20 条评估集 | 一页评估结果与失败案例 |
| Day 11-14 | 补测试、架构图、项目讲稿；仅在核心闭环稳定后选择一个加分项 | Git 仓库/本地运行说明、1 分钟和 5 分钟讲稿 |

两周结束时，即使没有任何加分项，也已经可以暂停项目开发，把时间转回简历、后端题和投递。

## 与 Voucher 的关系

只有同时满足下列条件时，才把场景命名为 Voucher Operations Agent：

- 你能用脱敏或自行构造的数据解释至少 2 条 Voucher 规则；
- 你愿意且能够回答“冲突怎么定义、数据从哪里来、为什么不能直接写配置”；
- 该命名不会让面试官期待你提供真实线上实现或业务指标。

否则采用中性的名称，例如 **Operations Knowledge & Task Diagnostics Agent**。技术主线完全不变，也更诚实、抗追问。

## 面试如何诚实表达

> 这是我为补齐 Agent 后端工程能力做的个人项目，不把它包装成线上生产系统。我刻意将范围收敛到受控 Tool、可持久化任务状态、失败处理、可观测性和离线评估。真实生产中还需要接企业 IAM、合规审计、队列集群与灰度治理；我在设计中保留了这些边界，但不会声称已经完成。

这个说法比声称“做了全套生产级平台”更可信，也能自然把讨论带回你已有的分布式后端经验。

## 停止规则（必要提醒）

- 连续两天卡在框架、部署或模型兼容问题：删减功能，退回最简单 SDK + 显式状态机。
- 核心闭环未完成前，禁止添加 UI、Multi-Agent、复杂 MCP 或真实业务接入。
- 每新增一个组件，必须能用一句话回答：它解决什么问题？失败时怎样处理？怎么测试？答不上来就不加。
- 项目累计投入超过两周仍未可演示：冻结新功能，先完成 README、Demo、测试和讲稿。
