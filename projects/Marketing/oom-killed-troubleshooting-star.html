Marketing OOMKilled 排障图解

先讲人话 证据链 内存判断 排除干扰 面试说法

先讲人话

这次问题不是“Go 代码 panic 导致服务退出”，而是容器内存超过 2GiB limit 后，被系统用 SIGKILL 杀掉。核心证据不是单独的 137，而是 OOMKilled、memory.events.oom_kill=1、以及 usage > limit 三者组合。

1. 先看现象

CMDB 显示 Container exited with status 137，并且 Running Instances 是 0 of 1。这个现象说明实例被杀或异常退出，但还不能单独下 OOM 结论。

排除干扰项

不要直接下结论

只看到 status 137 不能说一定是 OOM。137 是 128 + 9，表示 SIGKILL，也可能是人为 kill 或平台操作。

强证据组合

把 OOMKilled、memory.events.oom_kill=1、usage > limit 放在一起，才能把直接原因定性为容器 OOMKilled。

日志/现象 怎么解释 面试风险
SeaTalk webhook panic 可能是 reliable-event 中 recover 后记录的业务错误。 不能把 recover 后的 panic 直接说成容器退出原因。
smoke test retry 启动检查曾经 retry，但后续 passed。 不能把启动检查失败和 OOM 直接等同。
profiling report 可能只是 OOM 前最后输出的日志。 不能只凭最后一行日志判断根因。

后续定位路径

目标 做法
先恢复 UAT 可临时把 memory 从 2GiB 提到 3GiB 或 4GiB，先让实例恢复。
判断峰值还是泄漏 看 OOM 前 5 到 15 分钟 Grafana 内存曲线和业务日志。
查 Go 内存 看 pprof/heap、goroutine、Top alloc、对象保留路径。
查业务触发点 重点看批任务、consumer、scheduler、大查询、一次性大 slice/map、缓存增长和并发。

1 分钟面试说法

我排查过一次 Marketing UAT 容器异常退出。页面上只看到 Container exited with status 137，同时日志里还有业务 panic 和 smoke test retry，容易被带偏。我先从 CMDB task、STDOUT/STDERR 和 termination log 找直接退出证据，看到 exit code=137、memory.events.oom_kill=1，并且内存 usage=2150584320 超过 limit=2147483648，所以定性为容器 OOMKilled。然后我排除了 recover 后的业务 panic 和已通过的 smoke test retry，建议先临时扩容恢复，再结合 Grafana 曲线、consumer、scheduler、批任务和 pprof 继续定位业务根因。
