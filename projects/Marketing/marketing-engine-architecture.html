Marketing Engine 架构图解

先讲人话 核心流水线 触发方式 Processor 代码路径 面试说法

先讲人话

Marketing Engine 就像一个运营自动化流水线。运营在 Admin 配一个 Plan，说明什么时候触发、筛哪些用户、最后做什么动作；系统按配置自动消费事件、匹配人群、执行通知/发券/数据更新。

一句话记忆

Plan = Trigger + User Group Processor + Handler。面试时先讲这个公式，再展开三阶段：触发、筛选、执行。

核心抽象

Trigger

决定什么时候开始：Cron、MQ、实时事件。不同入口最终都汇聚到 PlanDispatch。

User Group Processor

决定对哪些用户执行：实时校验、定时拉人群、额外规则过滤，可用 AND/OR/Delay 组合。

Handler

决定做什么动作：发通知、发券、PNAR、Chat 文案、数据清洗、组合奖励。

Admin 配置 Plan

Admin 页面把运营动作配置成 Plan：包括触发方式、用户分组、Processor 参数、Handler 名称、Handler 参数和 Rule 参数。这里体现配置化能力，避免每次运营活动都发版。

三种触发方式

定时触发适合周期性运营活动。Scheduler 触发后，Marketing-Data 批量拉用户并推送到 Kafka，Marketing Engine 消费后进入 PlanDispatch。

Processor 怎么理解

先讲人话

Processor 就是一段可复用的筛选逻辑。配置里只存 processor code 和参数，运行时根据 code 找到具体实现，再用参数判断这个用户或这批用户是否命中。

技术关键词

策略模式、自注册、链式执行、AND/OR/Delay 组合、JSON 参数、占位符填充。

Processor 类型 适合场景 面试表达
EventCheck 实时事件/MQ 事件来了之后，判断事件字段是否匹配。 解决“这个事件是不是我要的用户动作或状态变化”。
SchedulePullUserList 定时任务批量圈人，从 ES 或离线数据源构造查询条件。 解决“周期性活动要先拉出一批目标用户”。
AdditionalCheck 触发后再做业务规则过滤，例如是否买过产品、是否在某个人群里。 解决“命中后还要不要二次过滤”。

1 分钟面试说法

我参与的 Marketing Engine 本质是一个配置化的运营自动化引擎。核心抽象是 Plan，一个 Plan 定义触发方式、目标用户筛选和最终执行动作。触发层支持定时、MQ 和实时事件，但最终都会汇聚到 PlanDispatch；筛选层通过 User Group 下的 Processor 链做 AND/OR/Delay 组合；执行层通过 Handler 插件完成通知、发券、PNAR 或数据清洗。这个设计的价值是把运营活动从代码发版变成后台配置，同时用 RuleCenter 复用通用条件判断，降低重复逻辑和改动风险。
