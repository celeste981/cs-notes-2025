先记住一句话

Marketing 用户组匹配本质是 membership check：给一个 user_id，判断它是否在某个目标人群里。优化点是把离线名单提前转成可快速查询的 Redis / LocalCache 结构，避免在线扫 DB、ES 或 S3。

面试主线

旧 Bloom / 固定 bitmap 有误判和内存浪费；Roaring Bitmap 做精准整数集合；Redis 落地用 high/low 分段、meta hash、Set/Bitmap/Run 三类容器；生命周期靠刷新、巡检、marker 和告警兜底。

0 Roaring 精准匹配误判概率
24 低位 bit 数，单容器覆盖 2^24 个 lowValue
2M 40/24 方案下单 bitmap 容器最大约占用
1500+ mepage 场景全局 QPS 样本，适合本地缓存减 Redis 压力

方案选型图

选型不是“全部上 Redis”。核心看数据量、并发、是否即时查询、是否允许误差。

MySQL

小名单、低并发、简单查询。优点是直接；缺点是不适合在线大规模 membership check。

LocalCache

mepage 这类高 QPS 热点分组。用 roaring64.Bitmap.Contains 在进程内判断。

Redis Roaring

大名单、需要精准匹配、不能每次扫文件。用 Redis 二级结构做快速判断。

RemoteLocalCache

Marketing 先把序列化 Roaring Bitmap 存 Redis，其他服务拉到本地判断。

场景 数据量 并发 查询存储 面试解释
Seller Promotion 名单 小 低 MySQL 低压场景不必引入复杂缓存。
mepage 资源位名单 大 高 Local Roaring Bitmap 高 QPS 下先保护 Redis，内存数量用上限控制。
货架 / Data tag 大名单 大 中低 Redis Roaring Bitmap 精准匹配，查询快，pod 重启不用重新加载全量名单。

64 位 user_id 怎么拆

当前方案用 LowBitNum=24：高 40 位做分桶，低 24 位放进桶内容器。

highKey

高 40 位：决定落在哪个 Redis 二级 key。

lowValue

低 24 位：决定桶内 offset。

公式：highKey = user_id >> 24，lowValue = user_id & 0xFFFFFF

highKey 536
lowValue 9934593

Redis 二级结构

查询先读 meta hash。meta 告诉你这个 highKey 应该用 Set、Bitmap 还是 Run。

Group Meta Hash

highKey -> containerType

例如：536 -> 2

ArrayContainer

Redis Set

稀疏段：用 SISMEMBER 查 lowValue。

BitmapContainer

Redis String bitmap

密集段：用 GETBIT 查 offset。

RunContainer

只记 meta

满段：highKey 存在且类型为 3，直接命中。

空分组 marker

__empty_group__ = RunContainer

表达缓存已初始化但无成员；正常查询不会误命中。

RemoteLocalCache

MarshalBinary()

标准 roaring64.Bitmap 序列化后写 Redis，其他服务拉到本地。

面试口述卡片

30 秒版本

Marketing 用户组匹配本质是判断 user_id 是否在某个名单集合里。旧 Bloom/bitmap 方案要么有误判，要么固定占用内存高。我们用 Roaring Bitmap 思路优化：本地高 QPS 场景用 roaring64.Bitmap，其他大名单用客户端改造的 Redis Roaring Bitmap。Redis 里按高 40 位、低 24 位拆分，稀疏用 Set，密集用 Bitmap，满段用 RunContainer，做到精准匹配且内存更可控。
